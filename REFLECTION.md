# Эссе: почему выбрала новостного агента, где он сломался и что дальше

## Почему эта задача

Идея информационного ассистента, который за одну команду достаёт свежие новости по любой теме, зацепила меня своей практичностью. Я часто ловлю себя на том, что трачу время на ручной поиск в браузере: открываю десяток вкладок, фильтрую кликбейтные заголовки, сверяю источники. Агент, живущий в терминале и делающий это автоматически, решает конкретную бытовую проблему ускорения доступа к фактам — причём без отвлечения на рекламу и лишние интерфейсы

Я выбрала трек А, потому что хотела на практике разобраться, как правильно встраивать внешние сервисы в логику современного LLM-агента. Новости — идеальная точка входа: API документирован, данные структурированы, а результат сразу виден и проверяем. При этом задача не сводится к «обернуть API в функцию» — нужно научить модель саму решать, когда вызывать инструмент, как интерпретировать ответ и что говорить пользователю. Этот баланс между автономностью агента и контролем над внешними вызовами мне и был интересен

Ещё один личный мотив — архитектурный. Мне хотелось не просто написать работающий скрипт, а построить систему, которую не стыдно показать: с разделением ответственности, абстракциями и готовностью к расширению. Трек А дал для этого отличным тренажером — один инструмент, один внешний API, но достаточно пространства для архитектурных решений

## Где агент сломался

### 1. Игнорирование ограничений по дате и времени

**Сценарий:** пользователь просит «новости про бабочек за вчера». Агент вызывает `get_news(topic="бабочки")`, но **не учитывает** указание «за вчера». Инструмент возвращает последние по дате публикации новости, среди которых оказываются статьи за первую половину апреля

**Что произошло:** схема инструмента `get_news` содержит только параметр `topic`, поля для фильтрации по дате отсутствуют. LLM, следуя спецификации, отбрасывает ограничение даты, потому что ей некуда его передать. Ошибки не возникает, но результат не соответствует запросу

**Вывод:** этот кейс вскрывает архитектурное ограничение — неполноту API инструмента. Даже умная модель не может скомпенсировать отсутствие нужных параметров. В реальном продукте я бы расширила `NewsTool` опциональными `from_date` и `to_date`, обновила JSON Schema в `parameters` и логику `execute()`, чтобы LLM могла корректно преобразовывать «за вчера» в диапазон дат и передавать их в NewsAPI


### 2. Ошибка 429 от NewsAPI

**Сценарий:** при частых тестовых запросах NewsAPI ответил ошибкой 429 (Too Many Requests). Агент перехватил исключение и вернул пользователю «Не удалось получить новости: 429 Client Error»

**Что произошло:** fallback-сообщение содержало техническую деталь (HTTP-код), непонятную конечному пользователю

**Вывод:** обработка ошибок внешних сервисов должна быть двухуровневой: для разработчика (лог с деталями) и для пользователя (дружелюбное сообщение). В идеале — с рекомендацией действия, например «Сервис новостей временно перегружен, попробуйте позже»

**Что сделала бы иначе:** заменил бы сырой текст исключения на маппинг HTTP-кодов в человекочитаемые сообщения и добавил бы стратегию retry с экспоненциальной задержкой

## Что сделал бы дальше при наличии времени

### Фильтрация по времени
NewsAPI поддерживает параметр `from` для ограничения выборки датой. Добавить в `NewsTool` ещё один опциональный параметр `date_from` — и пользователь сможет спрашивать «новости за вчера» или «только за эту неделю». Протокол `ToolProtocol` это позволяет без правок агента

### Сводка новостей
Сейчас агент перечисляет заголовки. Можно добавить второй проход через LLM: после получения 5 статей просить модель сгенерировать краткий абзац «Главные события за сегодня по теме X». Это улучшит user experience, особенно для широких тем, где заголовков много

### Второй источник новостей
Зависимость от одного API — точка отказа. Я бы добавил `GNewsTool` или `RssTool`, реализующий тот же протокол `ToolProtocol`. Агент мог бы вызывать оба и предлагать пользователю сводку с пометкой об источнике, либо реестр сам выбирал бы доступный инструмент (fallback-стратегия на уровне `ToolRegistry`)

### Telegram-бот
Оборачивание агента в бота — естественный шаг к usability. Новый `main_bot.py`, использующий `python-telegram-bot`, принимал бы команды `/news тема` и передавал их в `agent.run()`

### Кэширование запросов
При повторяющихся темах в ходе одного диалога (или между сессиями) можно сохранять результаты `get_news` в словарь с TTL. Реализовала бы как обёртку над `ToolRegistryProtocol` — `CachedToolRegistry`, которая перед вызовом реального инструмента проверяет кэш. Агент остался бы без изменений

## Рефлексия над процессом

Сборка агента оказалась интереснее, чем я ожидала. Техническая часть — вызов API, настройка LLM — далась относительно легко, но настоящее удовольствие принесла архитектурная работа. Я изначально думала, что в условиях ограниченного времени получится лишь прототип, однако желание попробовать что-то новое и сделать систему «красивой» подтолкнуло меня к продуманной структуре с протоколами и разделением ответственности.

Больше всего времени ушло не на код, а на решения: как разбить логику так, чтобы агент оставался гибким. Я перебирала трёх разных LLM-провайдеров, и ни разу не пришлось менять ядро — только конфиг. Это оказалось приятным моментом

Учитывая условия минимального времени, я изначально понимала, что что-то масштабное написать не получится, но было интересно попробовать ;)
